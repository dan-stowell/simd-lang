# GOLEX.md — a lexer for Go, in Strand

*2026-11-11. The first workload that is a compilation phase of a real language, checked against
that language's own implementation.*

`examples/golex.strand` (generated by `examples/golex_gen.py`: two working lines, a dozen short ones and 21 tables)
reads Go source and writes the token stream that `go/scanner` produces in its default mode:
every token's byte offset and kind, comments skipped, automatic semicolons inserted.
`explore/golex` is the reference, a few lines of Go around `go/scanner`.

## Is it right?

On the Go standard library — the 8,084 `.go` files under `GOROOT/src` that scan without
error, concatenated: 92,537,748 bytes — the two outputs are **byte-identical: 17,047,917
tokens**, on 1, 2, 3, 4 and 8 CPUs. `test.sh` repeats the comparison on part of the library.

A corpus of programs that compile says little about token boundaries nobody writes. The
fifth audit found three (`x.0`, `0a`, `...0`; REVIEWS.md, review 8), all in numbers. The word
automaton is now a transcription of go/scanner's `scanNumber`, and `tests/golex_fuzz.py`
compares the two lexers on random lines built from digits, dots, exponent and prefix letters,
operators, quotes and comments, keeping the lines go/scanner accepts without error: 1.3
million of them agree, on one core and on all.

What that does not cover: input `go/scanner` reports errors for (two files were left out; the
lexer does not diagnose anything), a leading byte-order mark, NUL bytes (taken as newlines). Identifier
characters above 0x7F are taken to be letters, which `go/scanner` checks properly; the corpus
has 50,582 such bytes and no disagreement, but an input with a non-letter there would differ.
Carriage returns were excluded from the corpus out of caution; the audit found no mismatch
with them.

## How fast?

Whole process (start, map the file, lex, write 136 MB of output to /dev/null), median of 9;
`go/scanner` is its scan loop alone over a buffer already in memory, best of 7, one thread
(it has no parallel mode):

| | time | |
|---|---|---|
| `go/scanner`, scan only | 549-608 ms | 153-168 MB/s |
| the Go compiler's own scanner (`cmd/compile/internal/syntax`), scan only | 497-513 ms | measured by the fifth audit's harness |
| the same in a process that reads the file and writes the tokens | 1,142 ms | |
| Strand, 1 CPU | 454-470 ms | 200 MB/s |
| Strand, 2 CPUs | 295-306 ms | (382 before the one-pass pool, below) |
| Strand, 3 CPUs | 213-219 ms | (319) |
| Strand, 4 CPUs | 171-177 ms | (204) |
| Strand, 8 CPUs | 116-135 ms | (131) 690-800 MB/s |

Strand's rows are the middle half of 21 runs, timed around `taskset` and the process.
(The same program on one core over the last day: 1,143 ms, 610, 537, 516, 448; the ten
milliseconds since are the price of getting numbers right. Peak memory is 294 MB for the
93 MB input.)

So: on one core Strand does the whole job, file to tokens, in about 50 ms less than the Go
compiler's scanner takes for the scan alone, and on eight cores in about a quarter of it.
(Not the same work: both Go scanners also build literal strings and check what they read;
this lexer produces offsets and kinds and diagnoses nothing.) It is not the several-fold
single-core win that the byte-lane primitives suggest on paper; the reasons are below and
are the work list.

## How it works

One line over the bytes:

1. **Context.** An 8-state automaton says what every byte is inside of: code, a `//`
   comment, a `/* */` comment, a string, a raw string, a rune. Its input class is made from
   the byte, the byte before it (`back`), and whether the byte is escaped (a 3-state
   automaton over backslashes). Two of its states exist only to get `/*/` and `*//` right.
2. **Words.** An 8-state automaton over the bytes that are code follows identifiers and
   numbers: decimal, hex, fraction, exponent. That is what makes `1e+5` one token and
   `x+5` three, and it needs one byte of look-ahead (`peek`) for `.5`.
3. **Operators.** A 4-state automaton does longest match: its state is how many bytes of
   the current operator have been read, and its input says whether the last two or three
   bytes form a longer operator (two table lookups on `back`, `back2`).
4. **Kinds.** At the first byte after a token everything about it is known from the byte
   before: its word state (identifier, integer, float), whether it ended in `i`, how long
   an operator it was and its last two bytes, which quote closed it. Three small tables
   turn that into the token's kind.
5. **Out of the byte line**: the positions where tokens start and end (`%`), and the kinds,
   packed (`^`). A newline outside strings counts as a one-byte token of kind 0.

Then one line over the tokens, for the one thing bytes cannot decide: an identifier is a
keyword if its first twelve bytes hash to one and are equal to it. Three short lines turn
"newline after a token that wants one" into semicolons and write the output.

Nothing in it is specific to Go beyond the tables and the two lines.

## One step past the lexer: package-level declarations

`examples/godecl.strand` is the lexer and three more lines. It writes, for every name
declared at package level (functions, methods, variables, constants, types), the offset of
the name and what it is. That is what a compiler's parser has to find before anything can
be resolved, and what `ctags` or an editor's symbol list is.

1. **Nesting**: +1 for every `(` `[` `{`, -1 for every closer, and a running sum over the
   tokens. On all cores, like any prefix sum.
2. **An 8-state automaton over the tokens** (kinds are bytes, so a line over tokens is a
   byte line, with the same automata as a line over text). Its input is each token's kind
   and whether it is nested not at all, once, or more. After `func` it waits for a name,
   passing over a receiver; after `var`, `const` or `type` it takes a list of names, or a
   parenthesised group with one list per statement; everything else it skips to the next
   semicolon at the right depth. The lexer's automatic semicolons are what make "one
   statement" visible without a grammar.
3. **A 4-state automaton** remembers which of the four keywords was last seen outside all
   brackets.

On the 8,041 files of the standard library that `go/parser` accepts (92.4 MB, 17.0 million
tokens) the output is byte-identical to a walk over `go/parser`'s declarations: **335,742
names**, on one core and on eight. `tests/go/decls.go` holds the shapes the library does not
dwell on (grouped and generic declarations, receivers of every form, declarations inside
function bodies that must not be listed), and `test.sh` runs both.

| | time |
|---|---|
| `go/parser`, parsing only, one thread (it builds the whole syntax tree) | 2,776-3,362 ms |
| Strand, lexer and declarations, 1 CPU | 492-506 ms |
| 2 CPUs | 324-341 ms |
| 4 CPUs | 189-231 ms |
| 8 CPUs | 131-151 ms |

The three lines add about 45 ms to the lexer on one core, under 3 ns per token. The
comparison with `go/parser` is not like for like: it produces a tree with every expression
in it, this produces a list of names. What the row says is that the first thing a parser
must establish — where the declarations are and what they bind — does not need a parser,
and that nesting, the part of parsing that looks most sequential, is a prefix sum.

## What it needed from the language

All added for this, all general (DESIGN.md):

- **8-state automata** (`x \t`), next to the 4-state ones.
- **`peek`, `back`, `back2`**: the line's own input one byte ahead, one and two behind.
  Loads, not carries, so they cost none of a line's eight carry registers.
- **Stored byte vectors read inside byte lines**, bytes **packed** out of a byte line
  (`v m ^x`) and read lane for lane on a dword line (`'x`), and literals up to ten digits.
- **Position sinks that run on all cores**: `%x` keeps its count in a sum carry, so the
  pool splits the line like a prefix sum.
- A **pool that runs such a line once, not twice.** A line with running sums used to run a
  dry pass on every core to learn where each range's results go and in what state it
  starts, then the real pass. For this line every running sum is the count of a sink, so:
  each automaton enters its range in the state a 4 KB warm-up leaves it in (checked against
  the range before afterwards, as always; about 3% of ranges guess wrong, and now only
  those are redone), each range writes its tokens to scratch memory of its own, and when
  the counts are known every core copies its piece into place. On two cores that took the
  lexer from 382 to 295 ms. `tests/pool_big.py` feeds it inputs built to defeat the guesses.
- **`bytesz`**: a byte line over the input and one zero byte after it.

## Where the time goes, and what is next

The CPU's own counters do work on this VM (through `perf_event_open`, user mode only), so
there is now a real profiler, `tools/perfprof.c`: cycles, instructions and samples of the
instruction pointer on every thread; `tools/whattime.py` maps the samples back to tokens of
the source. (The two tools written before I found that out, `simdratio.c` and `sample.c`,
are rougher instruments; the fifth audit measured how rough.) On one core the lexer runs
1,626 million instructions in 1,345 million cycles of user time, and about 100 ms more in
the kernel:

| share of samples | where |
|---|---|
| 75% | the line over the bytes |
| 21% | the keyword line over the tokens |
| 4% | semicolons and output |

`bench/primcost.py` measures what each primitive costs, per 64-byte chunk, on this CPU:

| primitive | cycles | instructions |
|---|---|---|
| add, min, and, or | 0.2 | 2 |
| compare with a constant | 1.8 | 4 |
| table lookup `@t` | 3.9 | 10 |
| tee and push (`:x ... x`) | 4.2 | 3 |
| multiply | 5.2 | 9 |
| 4-state automaton | about 50 | 45 |
| 8-state automaton | about 70 | 68 |
| pack `^x`, an eighth of the bytes selected | 24 | 25 |
| positions `%x`, an eighth selected | 48 | 35 |
| positions `%x`, nothing selected | 9 | 21 |

The byte line spends about 690 cycles on a chunk. Its four automata are 240 of them, its
three sinks about 110, its 19 table lookups 75, and the rest is some sixty tees, pushes and
comparisons. Three things follow that I had wrong:

- **Instruction counts mislead.** A table lookup is ten instructions and four cycles; an
  automaton is one instruction per cycle because nearly all of it is byte shuffles, and this
  CPU does about one 512-bit shuffle per cycle. Removing every byte multiply from the line
  (13% of its instructions) bought 1%, and a 128-entry lookup at half the instructions, tried
  and removed again, bought 1.5%.
- **The sinks' cost is the memory they write, not the compress.** `vpcompressb` is five
  cycles. A store to memory the process has not touched before costs 41 cycles per 32 bytes
  here, page fault included: 1.4 microseconds per page on this VM. The lexer touches about
  190 MB of new memory for its token vectors, which is the 100 ms of kernel time. On a
  machine with ordinary page-fault costs that would be a quarter of it.
- **The stub's constants were 48 bytes off a cache-line boundary** (the blob starts 112 bytes
  into a page), so every byte comparison and every automaton loaded across two lines. Fixed:
  a comparison went from 2.8 cycles to 1.8.

What the profilers found, in the order found:

- **The position sinks were 29% of the run.** Four compress-and-store rounds per chunk, with
  masked stores. Now one byte compress of the lane numbers and as many widen-and-store
  steps as there are results (usually one or two), unmasked on the serial path: 516 to
  448 ms. What is left of their 20% is mostly the first touch of the memory they write
  (two 80 MB vectors): about 85 ms of the 448 is the kernel, by `time`'s system time.
- **Comparisons through mask registers were slow**: compare into a mask, then mask into a
  vector. A lexer's flags are chains of them. They are now two or three plain vector
  instructions (xor or saturating subtract, then min with 1).
- **Byte multiplies are eight instructions**, and removing every one of them from the line
  (tables hand out pre-scaled values) took 13% of its instructions and 1% of its time: this
  line is not limited by instruction count. It executes about 880 instructions per 64
  bytes, 76% of them vector.
- **Two cells written by every thread every chunk** made eight threads slower than one.

Still true:

- **The token line does seven gathers per token**, at scalar-loop prices on this CPU, and
  most tokens are not identifiers and do not need them. SIMD lanes cannot skip work.
- **Eight cores do 3.8 times the work of one, not 8.** The byte line itself goes from 331
  to about 50 ms of each core's time; around it are ranges redone after a wrong guess while
  the other cores wait, first touches of fresh memory, and the lines that write the output.
- **Every vector is as long as the input.** 93 MB of source is 200 MB of fresh pages. A
  streaming form would reuse them.
- **Every flag is a 64-byte vector.** A lexer written by hand keeps its flags as 64-bit
  masks in general registers. I expected most from a mask type in the language; the cost
  table says otherwise: logic on byte vectors is nearly free here (0.2 cycles), and what a
  mask type would save is the comparisons' second half, perhaps 5% of the line.

A file need not end in a newline: the byte line runs one byte past the input (`bytesz`, added
for this), so the last token has a byte after it like every other.

Next, in the order the numbers above suggest: **not writing what need not be kept** — the
token positions exist only to be read once by the next line, and a runtime that ran the
lines block by block (the byte line over a few megabytes, then the token line over what that
produced, in memory both have already touched) would save most of the kernel time on one
core and more on eight; a cheaper automaton, if there is one; the keyword check only for
tokens that can be keywords; and then the same lexer for a second language to see what was
Go-specific.
