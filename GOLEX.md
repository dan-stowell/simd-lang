# GOLEX.md — a lexer for Go, in Strand

*2026-11-11. The first workload that is a compilation phase of a real language, checked against
that language's own implementation.*

`examples/golex.strand` (generated by `examples/golex_gen.py`: 2 working lines and 19 tables)
reads Go source and writes the token stream that `go/scanner` produces in its default mode:
every token's byte offset and kind, comments skipped, automatic semicolons inserted.
`explore/golex` is the reference, a few lines of Go around `go/scanner`.

## Is it right?

On the Go standard library — the 8,084 `.go` files under `GOROOT/src` that scan without
error, concatenated: 92,537,748 bytes — the two outputs are **byte-identical: 17,047,917
tokens**, on 1, 2, 3, 4 and 8 CPUs. `test.sh` repeats the comparison on part of the library.

What that does not cover: input `go/scanner` reports errors for (two files were left out),
files with carriage returns or a byte-order mark, and anything not in this corpus. Identifier
characters above 0x7F are taken to be letters, which `go/scanner` checks properly; the corpus
has 50,582 such bytes and no disagreement, but an input with a non-letter there would differ.

## How fast?

Whole process (start, map the file, lex, write 136 MB of output to /dev/null), median of 9;
`go/scanner` is its scan loop alone over a buffer already in memory, best of 7, one thread
(it has no parallel mode):

| | time | |
|---|---|---|
| `go/scanner`, scan only | 601 ms | 154 MB/s, 35 ns per token |
| the same in a process that reads the file and writes the tokens | 1,142 ms | |
| Strand, 1 CPU | 630-638 ms | |
| Strand, 2 CPUs | 465 ms | |
| Strand, 4 CPUs | 266-271 ms | |
| Strand, 8 CPUs | 211-219 ms | 430 MB/s |

Compiling the lexer: 0.77 ms. Peak memory: 403 MB for a 93 MB input.

So: on one core Strand does the whole job in about the time `go/scanner` takes for the scan,
and on eight cores in a third of it. It is not the several-fold single-core win that the
byte-lane primitives suggest on paper; the reasons are below and are the work list.

## How it works

One line over the bytes:

1. **Context.** An 8-state automaton says what every byte is inside of: code, a `//`
   comment, a `/* */` comment, a string, a raw string, a rune. Its input class is made from
   the byte, the byte before it (`back`), and whether the byte is escaped (a 3-state
   automaton over backslashes). Two of its states exist only to get `/*/` and `*//` right.
2. **Words.** An 8-state automaton over the bytes that are code follows identifiers and
   numbers: decimal, hex, fraction, exponent. That is what makes `1e+5` one token and
   `x+5` three, and it needs one byte of look-ahead (`peek`) for `.5`.
3. **Operators.** A 4-state automaton does longest match: its state is how many bytes of
   the current operator have been read, and its input says whether the last two or three
   bytes form a longer operator (two table lookups on `back`, `back2`).
4. **Positions.** Where tokens start and end leave the line as dword vectors (`%`). A
   newline outside strings counts as a one-byte token here.

Then one line over the tokens: kind from the first bytes and the word state at the end;
keywords by a perfect hash of the first twelve bytes, confirmed by comparing them;
operators by a perfect hash of (first byte, second byte, length); and a flag for "a newline
after this token is a semicolon". Two output lines drop the newlines that are not.

Nothing in it is specific to Go beyond the tables and the two lines.

## What it needed from the language

All added for this, all general (DESIGN.md):

- **8-state automata** (`x \t`), next to the 4-state ones.
- **`peek`, `back`, `back2`**: the line's own input one byte ahead, one and two behind.
  Loads, not carries, so they cost none of a line's eight carry registers.
- **Stored byte vectors read inside byte lines**, and literals up to ten digits.
- **Position sinks that run on all cores**: `%x` keeps its count in a sum carry, so the
  pool splits the line like a prefix sum.
- A **better guess in the pool's dry pass**: each automaton enters its range in the state
  a 4 KB warm-up leaves it in, and the guess is peeled off afterwards. With five carries
  feeding each other, guessing state 0 cost four retries per block; now 5 retries in 24
  blocks on this corpus.

## Where the time goes, and what is next

One core, 630 ms: the byte line about 355 ms, the token line about 265, output about 25;
about 145 ms of the total is the kernel faulting in 330 MB of vectors.

- **The byte line executes about 740 vector instructions per 64 bytes**, of which the four
  automata are under 200. The rest is table lookups (nine instructions each, fourteen of
  them), comparisons, and moving values to stack depths whose carry register is free.
  A line has eight carry registers and this one uses all eight.
- **The token line does about twelve gathers per token**, and gathers cost scalar-loop
  prices on this CPU (HARDWARE.md). Most tokens are not identifiers and do not need the
  keyword gathers; SIMD lanes cannot skip them.
- **The dry pass doubles the byte line's work on more than one core.**
- **A fixed-size cost**: every vector is as long as the input, so 93 MB of source means
  330 MB of fresh pages. A streaming form would reuse them.

Next, in order: carries for `prev` kept in memory, so that a line's budget is not eight
(that removes the padding and allows more to be fused); kinds computed on byte lanes at
the end of each token and packed, so the token line only does keywords; then the same
lexer for a second language to see what was Go-specific.
