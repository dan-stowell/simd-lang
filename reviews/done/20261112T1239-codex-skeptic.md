# CHARTER

Only the user edits this file. Agents read it at the start of every iteration.

## North star

A cold build of a real project whose stock build has a minutes-long critical path
produces a working binary that passes the project's own tests, in **2 seconds of wall
clock**, by saturating every core and squeezing every instruction and every byte moved
(network, disk, DRAM, L3, L2, L1).

### The approach: fuse the build DAG

A build is a DAG of actions (Bazel's, or `go build`'s action graph). Today every action
is its own process: it gathers its inputs, runs, and materializes its outputs (export
data, objects, archives) for the next action to read back. **Compile the DAG instead:**
treat the whole build as one program, executed in one address space across all cores
(later: a few machines, cut at edges where little data crosses). Intermediate outputs are
not materialized: they're handed over in memory, streamed across edges before their
producer finishes, and deduplicated across the graph. These are HPC techniques (fusion,
streaming, work-stealing, locality) applied to a build.

**The speed limit is reading the sources and writing the binary.** Everything between those
is overhead to be fused away or work to be parallelized.

The night of 2026-11-11 measured why this is the direction (JOURNAL iterations 9-14):
parsing and type-checking all of MinIO in one process takes 1.4 s wall and 7.4
core-seconds, against ~30 core-seconds across 1,312 compiler processes (the difference
is export data written and read back, and IR conversions). On top of that come 1,312
process starts, millions of page faults on fresh heaps, ~600 MB of objects written for the
linker to read again, and 8% of code compiled twice by different packages. Early export
(streaming one edge) took the chain from 38.5 s to ~12 s.

### SIMD and Strand

SIMD and data parallelism are means, not the goal. Strand is the tool for phases that are
data-parallel-shaped (scans over source bytes, layout by prefix sums, relocation blends,
histograms, joins over dense IDs). The trace decides where those are; don't force a phase
into Strand that the trace says is elsewhere (lexing+parsing is ~1% of compile CPU). When a
fused design creates a new data-parallel-shaped phase (e.g. one pass over all sources, a
whole-program symbol table, a layout pass instead of a linker), Strand is the default for it,
and leaving it needs an entry in `SCALAR_LEDGER.md`.

are diagnostics and are never reported as results.

Two more things the trace must show:

- **A fair stock row.** Next to plain stock `go build`, a cold stock `go build` with the same
  relaxations we use: `GOGC=off go build -trimpath -gcflags=all='-dwarf=false -l'
  -ldflags='-s -w'`. Our gain is measured against *that* row, so "new technique" is kept
  apart from "turned things off".
- **The materialization tax.** Per build: bytes of intermediates written and read back (export
  data, objects, archives), process starts, page faults, core-seconds outside the compiler's
  own phases. This is what fusion removes; it should fall rung by rung.

## Physics, not baselines

For each phase, compute the floor from measured machine limits (`HARDWARE.md`): bytes moved
divided by the bandwidth of each level, and instructions per byte divided by (cores × IPC ×
clock). **% of floor** is the score. Stock toolchains are a reference point for the
end-to-end number only. Beating gcc/go on a kernel is not a goal.

State the scale honestly: this VM has 8 vCPUs, so 2 s is 16 core-seconds. Rung 0 computes
whether the target's irreducible work fits in that; if it doesn't, say so, and report
"2 s on N cores" with N derived from the floor.

## The critical path is the enemy

Minutes-long builds come from dependency chains (package/crate graph, header re-parsing,
global type inference, generic instantiation, linking), not from slow inner loops. For
every phase, answer in writing: **what serializes this, and can the problem be reshaped so
it doesn't?** Don't assume; reshape before giving up. Duplicated work counts as a
critical-path bug.

## May relax

Optimization level, debug info, incremental builds, separate compilation, object-file
formats, the linker as a separate step, diagnostic quality beyond "error + location", any
internal format. Whole-program is fine. Changing Strand is fine.

## How the floors are computed

A floor is the larger of (bytes moved / measured bandwidth of the level they move through) and (bytes x modelled ticks per byte / (8 cores x 3.095e9 ticks/s)). The bandwidths are measured. The ticks per byte are budgets for a data-parallel implementation, set in `tools/trace/mktrace.py`: lex 2, parse 8, types 40, codegen 40. They are the weakest numbers in this file. The link floor is one pass over the objects in and the binary out at memory bandwidth: a copy floor, which says nothing about symbol resolution or relocation (no model for those yet). For scale: the Strand Go lexer measures 15 ticks/byte today (GOLEX.md), and the stock toolchain spends about 11,578 ticks per source byte end to end on MinIO.

## Does 2 seconds fit on this machine?

By the floors above, MinIO's irreducible work is about 6.5 core-seconds (815 ms on 8 cores), inside the 16 core-seconds that 2 s on this VM allows, so physics does not rule the target out here. The stock toolchain does 282 core-seconds of work for the same build: with it doing the work, 2 s would need 141 perfectly used cores, and its dependency chain (38,503 ms) would still be in the way. So the gap is 18x in work done and 19x in the critical path; both have to go.

## 2026-11-12 00:34 UTC — iteration 11: rung 5 for real. A baseline code generator inside the compiler moves the trace.

**Why inside the compiler.** The second skeptic review (REVIEWS.md) argued for a hybrid back end inside
the stock compiler rather than my outside one: keep its typing and its runtime lowering, intercept
functions before SSA, fall back for the rest. sbc had proved the seam, but from outside it has to redo
every lowering (range, maps, strings, interfaces, closures) and cannot ask for type descriptors. Before
committing, I measured the ceiling: the patched compiler recorded the operations in every function's
lowered tree (`SB_OPSTATS`, `tools/trace/opstats.py`; 209,794 functions for MinIO). With about 45
operations a code generator covers 35-40% of back-end time; with interface calls and type assertions,
most of it.

**Did.** `driver/baseline/sbbaseline.go` (1,750 lines, compiled into cmd/compile/internal/ssagen by
`driver/mkcompiler.sh`, on with `SB_BASELINE=1`). Every function reaches it before SSA. It walks the
tree that `walk` left and writes machine code directly: no SSA construction, no optimization passes,
no register allocation. Whatever it does not understand makes it give up (a panic with the reason,
recovered at the top, logged with `SB_BASELINE_LOG`) and the function goes to SSA untouched.
The design is the simplest one that is safe under the runtime:
- every variable lives in memory (register parameters in their ABI spill slots, locals and temporaries
  in typed frame slots); a value is in AX between two tree nodes and nowhere across a call;
- the frame is zeroed on entry and there is one stack map, every pointer word of every slot, live
  throughout (two entries: at entry only the parameters, afterwards also results kept on the stack);
- the whole body is an unsafe point, so the function is preempted only at calls;
- pointer stores outside the frame go through the write barrier; variables whose address escapes are
  allocated where they are declared, as the stock back end does.
It handles integers of every width, pointers, strings, slices, interfaces, structs and arrays; field,
index and slice expressions with their bounds panics; division and shifts with Go's corner cases;
static, closure and interface calls with register and stack arguments and results; wrappers; switches.
Not yet: closures' captured variables, defer, floating point, `append`, type assertions, intrinsics.

## 2026-11-12 02:00 UTC — iteration 13: floating point; two memory-safety bugs and a compiler race, found by stress

**Floating point** in the baseline: a float travels between tree nodes as its bit pattern in the
integer accumulator, so loads, stores, temporaries and copies needed no new code; arithmetic,
comparison (with NaN's rules), conversion and the calling convention use the SSE registers. 98% of
functions in the oracle's packages and 97% of MinIO's now bypass SSA. The devirtualize-and-inline pass
is skipped in baseline mode with `-l` (it has nothing to inline and the rest is optimization).

**The important part: bugs that only repetition finds.**
1. One run in five of the oracle died in compress/flate with a dump of heap words and no test failure.
   Repeating the tests (`-count=8`) at three collector settings made it reliable: `found bad pointer in
   Go heap`, and go/printer with `found pointer to free object`. The "object" in the report was a
   goroutine stack and the pointer was exactly one past the end of an allocation. The lowered tree
   computes such addresses on purpose (`&s[len(s)]`, the destination of a copy of nothing) and hands them
   straight to memmove; the stock back end keeps them in a register for three instructions. My design
   parked every pointer-typed intermediate in a stack slot that the collector reads for the rest of the
   function. Two fixes, both from one rule I should have started with: *an intermediate needs to be
   visible to the collector only if a returning call can happen while it waits.* Argument and operand
   temporaries are now unscanned unless that is the case (`sbMayCall`), and the compiler's own
   temporaries that only ever hold an unchecked element address get unscanned slots
   (`sbPassingAddresses`; found by mapping the reported stack address to a frame offset to a store
   instruction to a source line: `want = append(want, abcabc[:n]...)`).
2. One MinIO build in ten failed: the *compiler* crashed with `concurrent map read and map write`. I
   was calling the package symbol table from the parallel back-end workers to make keys for labelled
   break/continue. A map of the function's own now.

**Evidence after the fixes.**
- 15 packages x 8 repetitions x GOGC 5/20/100: clean.
- 107 standard-library packages x 3 at GOGC=10 with the build's flags: the only failures are four tests
  that count allocations, and the same four fail with the unmodified compiler at `-l`.
- `tests/minio_stress.sh`: the server at GOGC=5, 300 objects of mixed sizes written, read back, compared,
  listed, deleted, eight at a time: passes.
- Ten consecutive MinIO builds: ten successes.

**Trace.** MinIO cold, four runs: 16.4, 16.7, 17.5, 16.6 s. kube-apiserver cold: 29.1 s. No real change
from iteration 12: the functions that were left were few.

**What this says about the approach.** The baseline's safety argument was "everything is in memory and
always live, so the collector can never miss anything". True, and not the whole requirement: the
collector must also never *see* something that is not a pointer. Always-live maps trade one for the
other. The standard library's tests did not find it in a single pass; the same tests repeated under
collector pressure did, in minutes. The stress run is now part of the oracle.

**Scope check.** Most ambitious: unchanged (front end). What I am doing instead for the rest of the

## 2026-11-12 03:16 UTC — iteration 14: where the CPU really goes; huge pages (spike, positive); the giant package sharded

**Trace.** MinIO cold, four runs: **13.3, 12.3, 12.6, 12.9 s** (iteration 13: 16.4-17.5; stock 54.2).
kube-apiserver cold, two runs: **24.1, 25.2 s** (was 28.5-29.1; stock 86.3). Both pass their smoke tests;
MinIO passes the stress test. Configuration `08-huge-shard`.

**What moved it, largest first.**

1. *Explicit huge pages for the tools' heaps (weird-idea spike; -2.6 s on MinIO, -4 s on kube).* The
   question was why 20 of MinIO's 87 compile core-seconds are kernel time. Answer, counted from
   /proc/vmstat: the compilers run with the collector off, touch 30 GB of fresh memory, and take 7.8
   million page faults at about 3.6 us each (a 4 kB fault under KVM costs about fifteen times what
   zeroing the page does). This kernel has no transparent huge pages (HARDWARE.md) but it does have
   hugetlbfs. The patched runtime (`SB_HUGE=1`) maps each 4 MB piece of heap growth from the explicit
   pool, falling back to ordinary pages when the pool is empty; the first 4 MB of every process stay
   ordinary, so the thousand small compiles never touch the pool. One compile of `minio/cmd`: 4.1 s
   -> 3.0 s wall, kernel time 1.45 -> 0.29 s, and user time falls too (5.6 -> 4.9 s: fewer TLB misses).
   Whole build: faults 7.8 M -> 1.7 M; kernel 21 -> 11 core-s; user 71-78 -> 65-68. The linker built
   against the same runtime (`build/link-sb`, `-linker`) links in 1.28 s instead of 1.48.
   *Cost and caveat:* it needs `sudo sysctl vm.nr_hugepages=N` (3,072 = 6 GB for MinIO, whose peak use
   was 4.2 GB; kube exhausted 10 GB and fell back for the rest). `tools/trace/sb.sh HUGEPAGES=n`
   reserves the pool before the run and puts the old value back afterwards. Hugetlb memory is not
   counted by the scope's MemoryMax, so the kube run lowers that cap to 16 G. This is machine
   configuration, not a cache: it holds nothing from a previous build. It is still a decision for the
   user, so MORNING.md gives the numbers both ways. (The cheaper variant, `SB_POPULATE=1`: one
   madvise(MADV_POPULATE_WRITE) per 4 MB instead of a thousand faults, no pool needed: halves the
   kernel time of a big compile, about -2.5 core-s on the whole build.)

2. *The one giant package compiled as shards (-1.0 s on MinIO).* The utilisation timeline of the build
   has two idle stretches: the first two seconds (plan, then the runtime's front end alone) and the
   last five (`minio/cmd`'s front end on one core, seven idle). Shards now drop other shards' bodies
   before type checking (`sbShardFilesPre`), shard 0 type-checks everything (initialisation order needs
   that) and emits the data. Measured: a function shard has about 1.15 core-s of fixed cost (parse,
   declarations, imports, object), so sharding everything above 400 kB costs 108 core-s against 87 and
   loses; eight shards for `cmd` lose to four for the same reason; four shards for the one package
   above 3 MB win a second. kube's giant (`pkg/generated/openapi`, 19 s under SSA) takes 2 s with the
   baseline and is no longer the tail; kube is CPU-bound from start to finish.

3. *Denser baseline code (-5 core-s, binary 180 -> 160 MB).* An instruction census of the baseline's
   output for five library packages (68 k instructions against 28 k optimized): 54% frame loads and
   stores, 19% word-by-word copies through R8. Now: two words at a time through X14 (and zeroing from
   X15), call results stored straight into the destination variable when nothing has been emitted
   since the call (the stores are retargeted, not repeated), constants stored in one instruction, more
   operand forms loaded directly into argument registers (fields, lengths, `&x`, string constants).
   60 k instructions on the same sample. The assembler is the largest single item in the compile
   profile (12 core-s), so instructions not emitted are saved three times: generator, assembler, linker.

# LINKING.md — can linking be given a SIMD shape?

*2026-11-10. A design question, answered with a prototype of the core operations
(`explore/link.c`), not with a linker. One thread, this VM, a synthetic job with the
proportions of a large C++ program: 2,000 units, 1,000,000 symbols with 24-88 byte names,
3,000,000 references by name, 12,000,000 relocations, 250 MB of code. It leaves out most of
what a production linker does (archives, COMDAT and weak symbols, section GC, identical code
folding, string merging, debug info, dynamic tables, file I/O, threads), so the numbers say
what the core costs and what it could cost, not how a real linker would compare.*

## What a link is made of

| part | conventional shape | time | reshaped | time |
|---|---|---|---|---|
| **join**: reference -> definition | hash the name, probe a table, compare strings | 1,000-1,450 ms (260-360 ns per name) | compare 64-bit fingerprints the compiler already computed | 48-52 ms (12-13 ns) |
| | | | the same as a 4-round scatter race with SIMD gathers (Strand's own name resolution) | 93-103 ms (23-26 ns) |
| | | | the reference is `(unit, ordinal)`: nothing to join | 0 |
| **layout**: addresses | prefix sums | 3 ms | (already the right shape) | 3 ms |
| **imports**: one address per reference | random reads of a symbol table | 13-14 ms (4.5 ns) | (the same) | 13-14 ms |
| **relocation** | copy the code, then write 4 bytes per site | 78-79 ms | gather the values, then one pass that expands them into a mask of hole bytes | 61-63 ms, 37 of it my scalar clean-up of the value stream |

Fingerprinting every name once, read in order, costs 84 ms (21 ns per name, 2.7 GB/s with
an 8-bytes-at-a-time scalar hash).

## What that says

**The join is random access, and SIMD does not help it.** With strings gone, resolving a
name is one probe of a table too big for the cache: 12 ns. The scatter-race form, which is
branch-free and uses gathers for the lookups, is twice as slow as the scalar probe loop on
this CPU. That matches HARDWARE.md (a gather costs what a scalar load loop costs) and I
think it is fundamental rather than an accident of Zen 4: what bounds a join is how many
cache misses the memory system serves at once, and an out-of-order core already keeps
about as many in flight from a scalar loop as a gather does. It is data-parallel in the
sense that threads help; it is not SIMD-shaped.

**But 95% of the conventional join is not the join. It is strings.** Hashing a name is 21
ns; comparing it with the definition's copy, somewhere else in memory, is most of the other
240-340. A linker has to do this because the object file format hands it names. A compiler
has every one of those names in hand, hot, when it emits the reference.

**Relocation is already nearly a stream.** Sites are sorted by offset, so the writes march
through the output; the cost is a second pass over memory that has just been copied. Done
as one pass (code, a mask of hole bytes, a stream of values; `vpexpandb`) it is 1.25x
faster here and has no scatter in it. The values come from a per-unit table of import
addresses that fits in L1.

## The reshaping

Linking stops being a join when the inputs stop being strings and start being indices:

1. **References are `(unit, ordinal)` pairs.** The compiler resolves a name when it reads
   the other unit's interface, which it has to do anyway to check the use. The ordinal is
   the position of the definition in that interface. Nothing with a name in it reaches the
   link. (Fallback for formats that must carry names: a fixed-width fingerprint beside each,
   so the join never touches a string: 20x cheaper.)
2. **Layout is a prefix sum** over unit sizes, and over the export offsets inside each unit.
3. **Imports are one gather per reference**: `address = base[unit] + export[unit][ordinal]`.
4. **Relocation is a stream**: the compiler emits, per unit, the code, a bit mask of the
   bytes that are holes, and one import index per hole in order. The link gathers the
   values from the unit's import table and expands them into the holes.

Steps 2-4 for this job: 3 + 14 + 62 = **about 80 ms against 1.1-1.5 s**, on one thread,
and every step is a scan, a gather from a small table or a streaming blend. That is a shape
Strand can express, with one primitive it lacks (below).

**Do we need the link at all?** If code reaches other units through its import table at
run time (what position-independent code does through a GOT) step 4 disappears: the "link"
is layout plus filling the import tables, 16 ms for 250 MB of code, and the code pages are
never written, so they can be mapped straight from the compiler's output. The price moves
to run time: one indirection per cross-unit reference. And if every unit is given a fixed
region of the address space when it is created, step 2 goes as well and loading is one
mapping per unit; that trades away dense packing of code.

## What is lost

Ordinals make a unit's interface an ordered thing: reordering or removing an export
invalidates the units compiled against it, where names would have survived. Nothing here
does what link-time optimisation, section GC or identical code folding do; those are graph
problems and I have not looked for a shape for them. And the two things a real linker
spends much of its time on, reading inputs and writing the output, are untouched.

## The linker, written in Strand

The reshaped link is now a Strand program, `examples/link.strand`, 30 lines, checked byte for
byte against a plain C linker (`explore/linkjob.c ref`) on a job file both read: 2,000 units
of 64-192 KiB, 1,000,000 exports, 3,000,000 imports, 12,150,000 relocations, a 262 MB image.
The whole of it:

```
<raw                                              # the job file, as a byte vector (not copied)
...                                               # header fields and section offsets: scalar lines
~U 4 * Ousize + {raw :usz dup scan swap - >inb    # where each unit's code is in the file
usz 63 + 6 >> 6 << :al dup scan swap - >ubase     # where it goes: a prefix sum of aligned sizes
al $Tot
~U 4 * Ouexp + {raw dup scan swap - >exbase
~Ne 4 * :e4 Oexunit + {raw @ubase e4 Oexoff + {raw + >exaddr                 # every export's address
~Ni 4 * :i4 Oimu + {raw @exbase i4 Oimo + {raw + @exaddr >imaddr             # every import's: (unit, ordinal)
Tot ,img                                                                     # the image: zero bytes
~U :ui dup @inb Ocode + usz ui @ubase (raw )img end                          # one slice per unit
~Nr 4 * :r4 Orimp + {raw @imaddr r4 Orunit + {raw @ubase r4 Oroff + {raw + :pl - pl }img   # one dword per relocation
'img out
```

`examples/link2.strand` is the same linker with imports resolved by 64-bit fingerprint
instead of ordinal: exports race for slots in four tables, each import keeps the export
whose fingerprint matches. Same image.

What that shows, and what it does not:

- **The reshaped link is expressible, and it is short.** Every step is a line: prefix sums,
  gathers, a slice copy, a dword store. It took five new primitives (`<x`, `,x`, `(src )dst`,
  `}x`, `'x`), all of which the compiler's own back end now uses or could.
- **It does not beat the scalar C linker; it is 1.1x slower on one core.** Both spend about
  150 of their milliseconds in the kernel, faulting in the 262 MB image. Of Strand's user
  time, relocations are about 80 ms (6.5 ns each: four reads of the job, two table gathers,
  one store), the copy 40, imports 28.
- **Eight cores barely help**, because the two lines that do the work, the slice copy and
  the dword store, run on one thread: the runtime cannot know that their destinations do
  not overlap. They do not (offsets are sorted and disjoint), and that is checkable with one
  comparison against the previous element, so "an ordered sink may run in parallel when its
  destinations are increasing" is the next thing to build. An earlier version that zero-filled
  the image with a parallel line was *faster* on eight CPUs (210 ms) for one reason: the page
  faults were taken on eight threads.
- **The join costs what the prototype said**: about 110 ms more for 4,000,000 names by
  fingerprint, nothing by ordinal.
- A job this shape is bounded by memory traffic and page faults, not by arithmetic. SIMD
  buys little here; what the reshaping buys is that nothing in the link is a string or a
  hash-table probe, and that every line is one whose parallel form is mechanical.

## What this suggests for Strand

- **Slices and dword stores** turned out to matter more than the `expand` I first proposed:
  the copy is the larger part, and a dword store at a byte position is one instruction.
  Both are built (above), and the compiler's own back end uses them.
- **Ordered sinks in parallel under a monotonicity check** (above).
- **Separate compilation by slot number.** A Strand unit already refers to its vectors by
  slot; two units could share names as `(unit, slot)` and be joined by layout and expand,
  with no name table in the output. That would be a linker written in Strand whose every
  step is in the sweet spot, to measure against recompiling the whole program.

type emitter struct {
	ctxt  *obj.Link
	base  *src.PosBase
	plist *obj.Plist
	last  *obj.Prog
	line  uint
	bases  map[string]*src.PosBase
	rename func(string) string // source file path -> the name recorded in the line table
}

func newEmitter(pkgpath string) *emitter {
	ctxt := obj.Linknew(&x86.Linkamd64)
	ctxt.IsAsm = true // every symbol is referenced by name, like hand-written assembly
	ctxt.Pkgpath = pkgpath
	ctxt.DwTextCount = objabi.DummyDwarfFunctionCountForAssembler() // as cmd/asm: sizes the debug-info address references
	ctxt.Bso = bufio.NewWriter(os.Stdout)
	ctxt.DiagFunc = func(format string, args ...any) { log.Fatalf("sbc: "+format, args...) }
	x86.Linkamd64.Init(ctxt)
	return &emitter{ctxt: ctxt, base: src.NewFileBase("sbc", "sbc"), plist: new(obj.Plist), line: 1}
}

func (e *emitter) pos() src.XPos {
	return e.ctxt.PosTable.XPos(src.MakePos(e.base, e.line, 1))
}

func (e *emitter) add(p *obj.Prog) *obj.Prog {
	p.Ctxt = e.ctxt
	p.Pos = e.pos()
	if e.last == nil {
		e.plist.Firstpc = p
	} else {
		e.last.Link = p
	}
	e.last = p
	return p
}

// text starts a function: name is the full linker symbol name, argsize the bytes of stack the caller
// set aside for it (stack-assigned arguments and results, and the spill slots of register arguments).
func (e *emitter) text(name string, flags int, frame int64, argsize int32) *obj.LSym {
	s := e.ctxt.LookupABI(name, obj.ABIInternal)
	e.ctxt.InitTextSym(s, flags, e.pos())
	p := e.add(&obj.Prog{As: obj.ATEXT,
		From: obj.Addr{Type: obj.TYPE_MEM, Name: obj.NAME_EXTERN, Sym: s},
		To:   obj.Addr{Type: obj.TYPE_TEXTSIZE, Offset: frame, Val: argsize}})
	s.Func().Text = p
	return s
}

func reg(r int16) obj.Addr            { return obj.Addr{Type: obj.TYPE_REG, Reg: r} }
func mem(r int16, off int64) obj.Addr { return obj.Addr{Type: obj.TYPE_MEM, Reg: r, Offset: off} }
func imm(v int64) obj.Addr            { return obj.Addr{Type: obj.TYPE_CONST, Offset: v} }

func (e *emitter) ins(as obj.As, from, to obj.Addr) *obj.Prog {
	return e.add(&obj.Prog{As: as, From: from, To: to})
}

func (e *emitter) ret() { e.add(&obj.Prog{As: obj.ARET}) }

func (e *emitter) write(path string) {
	obj.Flushplist(e.ctxt, e.plist, nil)
	e.ctxt.NumberSyms()
	out, err := bio.Create(path)
	if err != nil {
		log.Fatal(err)
	}
	out.WriteString(objabi.HeaderString())
	fmt.Fprintf(out, "!\n")
	obj.WriteObjFile(e.ctxt, out)
	if err := out.Close(); err != nil {
		log.Fatal(err)
	}
	e.ctxt.Bso.Flush()
}

## 2026-11-12 00:34 UTC — iteration 11: rung 5 for real. A baseline code generator inside the compiler moves the trace.

**Why inside the compiler.** The second skeptic review (REVIEWS.md) argued for a hybrid back end inside
the stock compiler rather than my outside one: keep its typing and its runtime lowering, intercept
functions before SSA, fall back for the rest. sbc had proved the seam, but from outside it has to redo
every lowering (range, maps, strings, interfaces, closures) and cannot ask for type descriptors. Before
committing, I measured the ceiling: the patched compiler recorded the operations in every function's
lowered tree (`SB_OPSTATS`, `tools/trace/opstats.py`; 209,794 functions for MinIO). With about 45
operations a code generator covers 35-40% of back-end time; with interface calls and type assertions,
most of it.

**Did.** `driver/baseline/sbbaseline.go` (1,750 lines, compiled into cmd/compile/internal/ssagen by
`driver/mkcompiler.sh`, on with `SB_BASELINE=1`). Every function reaches it before SSA. It walks the
tree that `walk` left and writes machine code directly: no SSA construction, no optimization passes,
no register allocation. Whatever it does not understand makes it give up (a panic with the reason,
recovered at the top, logged with `SB_BASELINE_LOG`) and the function goes to SSA untouched.
The design is the simplest one that is safe under the runtime:
- every variable lives in memory (register parameters in their ABI spill slots, locals and temporaries
  in typed frame slots); a value is in AX between two tree nodes and nowhere across a call;
- the frame is zeroed on entry and there is one stack map, every pointer word of every slot, live
  throughout (two entries: at entry only the parameters, afterwards also results kept on the stack);
- the whole body is an unsafe point, so the function is preempted only at calls;
- pointer stores outside the frame go through the write barrier; variables whose address escapes are
  allocated where they are declared, as the stock back end does.
It handles integers of every width, pointers, strings, slices, interfaces, structs and arrays; field,
index and slice expressions with their bounds panics; division and shifts with Go's corner cases;
static, closure and interface calls with register and stack arguments and results; wrappers; switches.
Not yet: closures' captured variables, defer, floating point, `append`, type assertions, intrinsics.
