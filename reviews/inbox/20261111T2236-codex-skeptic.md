# CHARTER

## North star

A cold build of a real project whose stock build has a minutes-long critical path
produces a working binary that passes the project's own tests, in **2 seconds of wall
clock**, by saturating every core and squeezing every instruction and every byte moved
(network, disk, DRAM, L3, L2, L1).

Strand (SIMD-first, data-parallel by construction) is the means. It is the default tool
for every phase. Leaving it requires a measurement showing the phase is not
data-parallel-shaped, plus an entry in `SCALAR_LEDGER.md`. Strand changes whenever that
makes a phase of the real build more parallel.

## The one number

Every report leads with the **build trace** (`TRACE.md`, regenerated by one script): wall
clock per phase of the end-to-end build, the critical path, and core utilization.

    phase            ms    cores busy   bytes moved   floor ms   % of floor
    fetch (separate)
    read inputs
    lex/parse
    resolve/types
    lower/codegen
    link
    write output
    TOTAL / crit path

A change matters only if it moves this table or unblocks a rung that will. Microbenchmarks
are diagnostics and are never reported as results.

## Physics, not baselines

For each phase, compute the floor from measured machine limits (`HARDWARE.md`): bytes moved
divided by the bandwidth of each level, and instructions per byte divided by (cores × IPC ×
clock). **% of floor** is the score. Stock toolchains are a reference point for the
end-to-end number only. Beating gcc/go on a kernel is not a goal.

State the scale honestly: this VM has 8 vCPUs, so 2 s is 16 core-seconds. Rung 0 computes
whether the target's irreducible work fits in that; if it doesn't, say so, and report
"2 s on N cores" with N derived from the floor.

## The critical path is the enemy

Minutes-long builds come from dependency chains (package/crate graph, header re-parsing,
global type inference, generic instantiation, linking), not from slow inner loops. For
every phase, answer in writing: **what serializes this, and can the problem be reshaped so
it doesn't?** Don't assume; reshape before giving up. Duplicated work counts as a
critical-path bug.

## May relax

Optimization level, debug info, incremental builds, separate compilation, object-file
formats, the linker as a separate step, diagnostic quality beyond "error + location", any
internal format. Whole-program is fine. Changing Strand is fine.

## How the floors are computed

A floor is the larger of (bytes moved / measured bandwidth of the level they move through) and (bytes x modelled ticks per byte / (8 cores x 3.095e9 ticks/s)). The bandwidths are measured. The ticks per byte are budgets for a data-parallel implementation, set in `tools/trace/mktrace.py`: lex 2, parse 8, types 40, codegen 40. They are the weakest numbers in this file. For scale: the Strand Go lexer measures 15 ticks/byte today (GOLEX.md), and the stock toolchain spends about 11,578 ticks per source byte end to end on MinIO.

## Does 2 seconds fit on this machine?

By the floors above, MinIO's irreducible work is about 6.5 core-seconds (815 ms on 8 cores), inside the 16 core-seconds that 2 s on this VM allows, so physics does not rule the target out here. The stock toolchain does 282 core-seconds of work for the same build: with it doing the work, 2 s would need 141 perfectly used cores, and its dependency chain (38,503 ms) would still be in the way. So the gap is 18x in work done and 19x in the critical path; both have to go.

## Corrections after the audit (2026-11-10)

AUDIT.md, defect 3, found that parts of this file claimed more than `hw/probe.c` measured.

- **Four "executes" probes did not contain their instruction.** The compiler had turned the
  SSE2, AVX and AVX2 intrinsics into other code and the ADX probe into a plain `adc`. They
  are now written in assembly, `hw/check_probe.py` checks every probe against its
  disassembly, and the four still execute. (The audit found two; the check found four.)
- **The scalar prefix-sum baseline overflowed a signed integer** (undefined behaviour). It
  now uses unsigned arithmetic. The scalar figure depends on the build: 0.85 ticks/element
  with `-march=native`, 1.69 with the documented plain `-O2` (five runs each, stable to
  0.02); the SIMD kernel is 6.7 per 16 elements either way. So the ratio is 2x or 4x, not
  "2x" as this file said; the second audit caught that my own correction contradicted the
  table. The table now gives the range.
- **"64 MiB table, random" is mislabelled.** That gather uses the same 1,024 indices every
  repetition, so it touches at most 1,024 cache lines below 16 MiB. It measures a gather
  across many pages, not a memory-bound traversal of 64 MiB.
- **"40x worse than vpermi2b"** compares two different kernels (a 128-entry byte table
  against a widened dword gather with four times the output). It is the cost ratio of those
  two representations, not of one task done two ways.
- **Costs are for load + operation + store kernels**, not instruction latencies. "Gather
  costs what a scalar load loop costs" is true of the kernel totals and does not show that
  gather lanes are serialised inside the CPU.
- **"No AVX-512 frequency penalty"** rests on one before/after comparison of a scalar loop.
  It is an observation about that run on this VM.
- The audit's rerun reproduced most rows closely; two differed: `vpcompressb` to a register
  8.7 (4.9 here) and `vpscatterdd` 27.6 (20.8 here).

## What this means for the design

1. **Zen 4's AVX-512 is a better instruction set, not a wider datapath.** zmm costs exactly
   two ymm ops. The win is masks, compress/expand, vpermb, conflict detection, and halved
   loop overhead — not 2x lanes. Design for the *instructions*.
2. **Gather and scatter kernels are no faster than scalar loops here.** A load + gather +
   store kernel costs what the scalar loop costs, a scatter kernel more. That is a
   statement about kernel totals; it does not show how the CPU executes the lanes. They buy
   *branch-freedom and fusion*, not speed, and every gather/scatter in the compiler is
   counted in SCALAR_LEDGER.md for that reason. Classify bytes with compares or byte
   permutes, never with a gathered table.
3. **Compress to a register, store full width.** Output arrays therefore need >= 64 bytes
   of slack after the logical end.
4. **Prefix sum is 2-4x over scalar** (the carry is a real dependency), far from the 9x of a
   plain add. Scans are the idiom, but they are not free; prefer designs where one scan
   serves many purposes.
5. Arrays that spill L1 (32 KiB = 8192 dwords) triple the cost of everything (5.2 vs 1.9
   ticks for add when three 16 KiB arrays were used). A compiler whose working set is
   "one dword per source byte" leaves L1 at 8 KiB of source. Byte lanes would be 4x denser.

## Addendum 2: what automata added (after the audit)

| # | island | size / cost | why |
|---|---|---|---|
| 21 | **The stub grew again**: constants for the automaton stencils, a dry-pass exit, derivation of carries one chunk before each range, and a warm-up chunk at the start of every real pass. | about 900 instructions, 5,376 bytes (was 787 and 4,480), copied into every binary; per-thread blocks are 8 KiB | Composing ranges and making dependent `prev` carries exact are thread-pool protocol. |

## The build driver (2026-11-11)

`driver/main.go` (`build/sb`) is Go, not Strand. It is orchestration: it starts processes, keeps a ready
queue ordered by the cost of the chain above each package, and hands out CPU tokens. None of that is

downstream consumes yet.

1. **Early export leaves two major serial bottlenecks intact.** The patch publishes exports **after type checking, inlining decisions and escape analysis** ([early_export.py](/home/exedev/strand-w/driver/early_export.py:2)). Those stages still chain across imports. It also does nothing to parallelize a single giant function: the four JSON VM packages take **2.599 + 2.806 + 4.985 + 4.751 = 15.141 s** along the stock dependency chain, with their giant functions compiled on one core. Finally, the current **3.077 s link at 1.7 cores busy** starts after all compilation finishes ([TRACE.md](/home/exedev/strand-w/TRACE.md)). Early export attacks package waiting; it does not remove these underlying serial computations.

2. **The link floor of 3 ms is a copy floor, not a linker floor.** Its calculation is literally binary size divided by memory bandwidth ([mktrace.py](/home/exedev/strand-w/tools/trace/mktrace.py:278)): **147 MB / 43.09 GB/s ≈ 3.4 ms**. Linking must also load object metadata, resolve symbols, traverse reachability, assign addresses and apply relocations. The skeleton produces **949 MB of archives**; even one complete streaming pass over that volume would cost **22 ms**, before graph work. Actual bytes visited and dependent memory accesses determine the limit—not output size. **The repository has not established that limit.** The current implementation takes **3.077 s**, and final disk output has a separate **163 ms** bandwidth floor. Likewise, the frontend’s **40 ticks/source-byte for types** is a budget, not evidence that dependency depth disappears.

3. **The direction becomes a dead end if scheduling stock work remains the strategy.** The current build consumes **265 core-seconds**: perfect utilization of eight cores still means **33.1 s**, against a **16 core-second** budget. The largest stock component is code generation, **169 core-seconds**. Meanwhile, Strand adds **213 ms** of lexing whose tokens are discarded downstream ([TRACE.md](/home/exedev/strand-w/TRACE.md); [main.go](/home/exedev/strand-w/driver/main.go:291)). I would build a shared, compact whole-program representation: parse files independently, separate declaration availability from body compilation, schedule functions globally, and emit minimally optimized code with parallel layout/relocation. That replaces work and removes package barriers; compiler flags and early export are useful experiments, not the destination.

4. **The ambitious overnight step is a consumed replacement backend slice.** Export typed function IR from stock Go; implement Strand machine-code emission for a bounded subset of real functions, retaining stock emission for unsupported functions and stock assembly/linking. Feed those replacements into an actual MinIO binary and differential-test behavior. This is an overnight integration spike, not a credible promise of a complete Go backend or a finished charter rung. It attacks the **169-core-second** component and establishes the replacement boundary. The journal’s original reason for avoiding it—“there is no driver yet”—has expired. Its latest stated reason is that early export and compiler flags are cheaper unexplored cuts ([JOURNAL.md](/home/exedev/strand-w/JOURNAL.md:43), [latest scope check](/home/exedev/strand-w/JOURNAL.md:74)). That is a sequencing preference, not a technical prerequisite.
